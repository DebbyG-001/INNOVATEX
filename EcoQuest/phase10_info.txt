PHASE 3 — MONEY REPRESENTATION
==================================================

Inspect how money is currently represented.

Do NOT blindly migrate the entire database.

Determine the safest migration strategy based on the current schema.

The target should avoid floating-point financial calculations.

For NGN, a sensible representation is integer Kobo.

For example:

₦100,000
=
10,000,000 Kobo

Financial calculations should use integer-safe arithmetic.

If the existing schema already uses a safe NUMERIC/DECIMAL representation correctly, do not migrate unnecessarily.

Create clear conversion utilities if needed.

==================================================
PHASE 4 — AUTHENTICATION AND USER ISOLATION
==================================================

This is one of the highest-priority changes.

Never trust:

userId

coming from:

- request body
- query parameters
- client state
- localStorage

for protected financial operations.

Derive the authenticated user from the existing server-side authentication/session mechanism.

Create a centralized authentication resolver if the project does not already have one.

Every protected resource must enforce ownership.

For example:

SELECT *
FROM bills
WHERE id = $billId
AND user_id = $authenticatedUserId;

The same principle applies to:

- accounts
- transactions
- transfers
- bills
- goals
- missions
- gamification
- onboarding/placement

A user must never be able to manipulate another user's data by changing an ID.

==================================================
PHASE 5 — ATOMIC FINANCIAL OPERATIONS
==================================================

This is extremely important.

Financial mutations must be atomic.

For:

- add money
- transfer
- bill payment
- goal contribution

use PostgreSQL transactions where appropriate.

Conceptually:

BEGIN

validate
authenticate
authorize

lock relevant account row

check balance

update balance

create transaction/ledger record

update related domain state

update gamification/event state

COMMIT

If anything fails:

ROLLBACK

Prevent:

- double spending
- partial updates
- balance inconsistencies
- duplicate charges
- duplicate rewards

Use row-level locking where required.

Do not introduce a complicated financial system if the existing demo only requires a simple reliable ledger.

==================================================
PHASE 7 — ADD MONEY
==================================================

The app is a banking DEMO.

Users need to be able to add simulated money.

This is NOT a real payment gateway.

When the user adds money:

1. Authenticate user
2. Validate amount
3. Update account
4. Create transaction/ledger record
5. Trigger appropriate gamification event
6. Commit atomically
7. Return updated state

Do not simply update a React variable.

PHASE 10 — BILL PAYMENT
==================================================

Paying a bill must be a real backend mutation.

Flow:

authenticate
↓
validate
↓
verify ownership
↓
check balance
↓
lock account
↓
deduct balance
↓
create transaction
↓
mark bill paid
↓
trigger gamification
↓
create next recurring bill if necessary
↓
commit

Prevent duplicate payment.

If the payment request is retried, it must not charge the user twice.
